# 阶段缓存与中文检索基线

## 缓存的一次读写

Rust core 的 `TaskStore` 在应用私有目录中保存缓存。SQLite v3 记录每个阶段键的文件编号、
BLAKE3 摘要、字节数、最近使用顺序和任务引用。文件名由 core 生成。源标识、URL、模型名和查询文本均不参与路径拼接。

1. 调用方用 `StageIdentity::key` 声明来源、内容版本及指纹、分 P、阶段、模型及版本、算法、
   Prompt 和 Schema 版本、推理参数以及直接输入。参数为 JSON 对象，递归按键排序，以紧凑 UTF-8
   序列化后计算 BLAKE3。数组顺序有意义，非有限数报错。参数数值保留精度，生产者应稳定使用同一种数值写法。
2. `cache_get` 对未发布的键返回空值。命中时从同一个文件读出字节，复核长度与摘要，再更新使用顺序。
   文件丢失、截断或同长度篡改返回 `CacheIntegrity`。调用方可以重新执行该阶段并发布修复结果。
   直接输入带上游键和实际字节摘要，因此重新生成的上游内容也会使使用它的下游失效。
3. `cache_put` 在 SQLite 写事务内写同目录临时文件，同步并重新读取验证，使用与迁移备份相同的持久化发布操作，
   然后提交新索引。替换使用独立文件名。提交前出错，先前的索引和文件仍可读。提交后旧文件清理出错时返回
   `CacheCleanup`，新索引已经生效。启动或显式清理会回收遗留的暂存文件和失去索引的已发布文件。
4. 读写时可在同一事务绑定任务。显式调用 `trim_cache(budget)` 按最近使用顺序淘汰，并返回剩余的已索引内容字节数。
   未完成任务（含暂停和中断）的引用跨重启保留。预算低于受保护内容时，返回值可超出预算。
   同键受保护时允许按原摘要修复，改写为不同内容会返回 `CacheInUse`。终态任务的引用在清理时释放。

预算按有效载荷统计。SQLite、备份、文件系统分配以及发布过程中的两代文件另占空间。当前接口以单个字节缓冲区收发产物，
并在校验时持有写事务，大产物及并发 I/O 吞吐尚未测量。启动清理扫描文件名，已索引文件在读取时逐个校验。

回归覆盖规范字节金样本、依赖失效与独立阶段命中、同长度损坏、文件缺失和截断、重建、LRU 与活动引用、
暂存失败、索引提交失败后的孤立文件、SQLite 返回 SQLITE_FULL 后重启和重试，以及 v2 升级后保留既有结果。
测试使用临时目录、真实 SQLite 和合成字节。物理掉电及写满真实磁盘尚未实测。
哈希复用 [BLAKE3 Rust 实现](https://github.com/BLAKE3-team/BLAKE3)，锁定版本 1.8.7，可按 Apache-2.0 使用。

## 中文检索对照

本次比较的目标是**按字面子串找到字幕片段**。语料有 24 个手写合成模板，每个模板附 32 个样本编号，共 768 条记录。
22 条查询各有手工标注的模板编号，包含单字、跨词边界、英文大小写、代码、标点、引号与无结果查询。
召回按查询与目标行的配对数统计，误报单独计数。相关性排序、语义同义词和繁简转换另需语料与评价方法。

三个方案共用原文表并使用 FTS5 无内容索引。预分词使用固定词表最长匹配，未知汉字逐字切分，连续英数为一个词。
Bigram 按相邻两个 Unicode 字符取词。这两组把词编码为十六进制后交给 ascii tokenizer，保留标点和词边界。
Trigram 直接使用 SQLite 内置 tokenizer。Bigram 的单字、trigram 的一至二字走原文 `instr` 扫描。
实验统一折叠 ASCII 大小写，MATCH 使用双引号字面短语，嵌入引号成对转义，SQL 参数绑定查询值。
[SQLite FTS5 tokenizer 文档](https://www.sqlite.org/fts5.html#tokenizers)

| 方案 | 中文短词 | 中文长串 | 混合英文和代码 | 标点与字面操作符 | 误报 | 索引增量 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 固定词表预分词 | 288/512 | 96/96 | 192/224 | 160/160 | 0 | 60 KiB |
| Bigram + 单字扫描 | 512/512 | 96/96 | 224/224 | 160/160 | 0 | 76 KiB |
| FTS5 trigram + 短词扫描 | 512/512 | 96/96 | 224/224 | 160/160 | 0 | 72 KiB |

例如，预分词把“数据库”作为一个词，查询“据库”会漏掉该行。Trigram 的短词扫描能找回它，但每次都要遍历原文。
本轮将 trigram 加短词扫描用作后续基线，理由是召回完整、无需自有分词器，索引也小于 bigram。
Bigram 在本批查询上更快，后续有代表性的短词负载时应保留这一对照。

| 方案 | 建索引 p50 / p95（ms） | 热查询整批 p50 / p95（ms） |
| --- | ---: | ---: |
| 固定词表预分词 | 6.015 / 6.614 | 1.479 / 2.099 |
| Bigram | 6.545 / 7.750 | 1.972 / 2.734 |
| FTS5 trigram | 5.217 / 5.730 | 2.702 / 3.398 |

复跑命令如下。固定输入、标注、分词规则与统计代码在同一[实验源文件](../crates/core/examples/chinese_search.rs)中。

```text
cargo run --release --locked -p videosift-core --example chinese_search
```

本次使用 Windows x64、Core Ultra 9 185H、平衡电源模式、Rust 1.100.0 MSVC、随库 SQLite 3.54.1。
每种方案在单线程中创建 5 个独立文件库，计时从建索引到 optimize 并提交，排除生成原文、编译和启动进程。
索引增量为同一数据库建索引前后文件长度之差，页大小 4096 字节。每库预热一整批后再测 10 批，共 50 批；
每批计入 22 次查询及所有结果行的读取，分位数按最近秩计算。操作系统文件缓存未清空。
重复模板便于复验，生产语料规模、短词比例、磁盘冷读及端到端搜索延迟仍待测量。
