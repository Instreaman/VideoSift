# SQLite 任务存储

Rust core 的 `storage::TaskStore` 接收应用专用的本地目录。打开成功后可提交任务、
派发、保存步骤检查点、暂停、取消和完成。数据库行号供 core 内部定位任务。
公共 IPC、内存调度器的句柄和进程监管接口沿用已有契约。

## 事务裁决

同一 core 可用 `writer()` 获得独立连接。每次派发在数据库内生成新的 128 位执行票据。
处理执行结果时，先取得 SQLite 写事务，再读取该任务的票据与状态，复用
[状态机](TASK_STATE.md)裁决。不同连接并发操作时以成功提交的事务为准。

- 先接受取消时，任务进入 cancel_requested。迟到的完成请求返回错误，保留先前已提交的检查点。
  持有效票据确认清理后，任务进入 cancelled。
- 先完成时，最终检查点、输出引用、succeeded 和票据失效在同一事务中生效。后续取消返回 succeeded。
- 提交失败时，调用方收到错误。另一连接释放读锁后可用原票据重试。
- 调用方先暂存并验证实际产物。此层校验引用非空、长度和控制字符，仅持久化引用。
  [阶段缓存](CACHE_SEARCH.md)负责内容核验与清理。调度器和真实产物的端到端接入留待集成验收。

## 迁移与备份

`tasks.sqlite3` 用 application_id 标识文件归属，用 user_version 编号。新库从空库依次建表，
v1 存储状态，v2 增加执行票据、检查点、结果引用及活动票据唯一索引，v3 增加缓存索引和任务引用。已有库先用只读连接
检查已提交的版本和归属，包括仍在 WAL 中的版本号。若 SQLite 必须回放热回滚日志才能读取版本，
core 在持有独占锁期间将主库和日志复制到应用目录内的临时子目录，在副本上回放并检查。
此路径需要容纳这两份文件的额外空间。预检通过后在写事务内复核，复核通过前关闭连接也禁止回写 WAL。
升级已有库时，用独立只读连接调用 SQLite 在线备份，已提交到 WAL 的行随快照保留。

备份成功后才在同一写事务内升级表结构与版本号。备份先写同目录临时文件，同步后以
`backups/tasks-v<旧版本>-*.backup.sqlite3` 发布，每次重试使用独立名称。备份目录应继承应用私有目录权限。
Windows 使用同卷写穿透移动发布最终名称。Unix 发布后依次同步备份目录及其父目录，
确保新文件名和新建的备份目录均已落盘。发布或同步返回错误时立即停止迁移，重试会保留已有快照。
备份失败或 SQLite 报空间不足时，旧库可继续读取并重试。高版本及无法识别归属的库返回错误。
保留 SQLite 原有日志模式。新库采用默认回滚日志，当前未测量 WAL 性能或备份保留周期。

## 重启

core 持有操作系统文件锁 `tasks.lock` 至最后一个写连接释放。进程退出后系统释放锁，
第二个活跃 core 打开同一目录时收到占用错误。在返回首个写连接前，一次事务将 running、
pause_requested、cancel_requested 标为 interrupted，清除旧票据，保留已提交检查点。
其他状态原样保留。调用方可按行号分页列出中断任务，用户显式恢复后才可重新派发。
原票据即使在新执行已进入 running 后到达，完成、覆盖检查点和确认取消都会被拒绝。

## 验证

测试使用临时目录和真实 SQLite 文件，覆盖两种提交顺序、并发写者、COMMIT 忙时的回滚与重试、
包含 WAL 数据的迁移备份、备份失败、版本过新拒写、两次重启以及子进程跳过析构直接退出。
迁移测试使用 max_page_count 让 SQLite 返回 SQLITE_FULL，随后核对旧表结构、旧版本、数据与备份。
审阅回归覆盖遗留 WAL 中的高版本、两次检查之间变更版本、热回滚日志、备份名称冲突，
以及 Unix 上备份目录或父目录同步失败。高版本拒写会逐字节比较原主库和遗留日志。
物理掉电、真实磁盘耗尽及性能指标尚未实测。

实现复用 [rusqlite](https://github.com/rusqlite/rusqlite) 的 bundled 和 backup 功能，
通过锁文件固定 SQLite 源码依赖，Windows 无需另装数据库服务。
备份与事务语义见 [SQLite 在线备份](https://www.sqlite.org/backup.html) 和
[SQLite 事务](https://www.sqlite.org/lang_transaction.html)。
